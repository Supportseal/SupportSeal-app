# Product positioning

## Who and why

For developers and small teams supporting several independent products, the problem is fragmentation: separate support addresses and widgets, one shared team, and too little application context when answering customers.

## Positioning hypothesis

**One support desk for everything you build.** Put chat and support email on every Product; work in one inbox with the user and application context you chose to send. Run the published software yourself or choose managed hosting.

The strongest combination is portfolio-wide support, first-class email, explicit developer context, low-friction integration and a credible self-hosted option. The primary demonstration should show two visually distinct Products sending messages into one inbox, with a useful context panel and an email reply.

## Message hierarchy

1. **Outcome:** handle support for all the products you build in one place.
2. **How:** Product-specific chat and email, unified inbox and intentional app context.
3. **Choice:** self-host the same core support experience or use managed hosting.
4. **Economics:** hosted plans based mainly on Conversation volume rather than a per-Product or paid per-seat tax.

Speak plainly to a founder supporting several apps. Lead with the support workflow; show the interface early. Keep claims aligned with shipped behaviour and avoid invented proof, customer logos or comparative claims without a fresh check. This is positioning direction, not final homepage copy or a live competitor/pricing survey.

## First-use promise

The first meaningful success is receiving and answering a message from one Product. The next is adding another Product and seeing both in the same inbox. Onboarding and marketing should make these outcomes easy to understand and test.
