# Functional requirements — V1

This file specifies observable behaviour, not framework, provider or database choices. Requirement IDs are stable references for acceptance tests. [PRD.md](PRD.md) owns scope and intent.

## Account and Products

- **FR-ACC-01** A person can register, create a Workspace, invite users and sign in. An Admin manages Workspace, Products, users, channel settings and hosted billing. An Agent can operate the inbox. V1 has only these two roles. A user without Workspace access cannot read or change its data.
- **FR-PROD-01** An Admin can create, edit and archive multiple Products, each with a name, primary colour, one or more domains, domain allowlist, public widget key and support-email configuration. V1 branding is name and primary colour only. Archiving prevents new Product interactions while preserving historical support records until deleted.
- **FR-PROD-02** A Product's branding and identity are visible in its widget and in every related inbox view. A Workspace can have unrelated Products without requiring separate agent accounts.

## Inbox and conversations

- **FR-INBOX-01** Authorised agents see Conversations from all Products in their Workspace, recognise Product and channel at a glance, filter by Product and return to the combined view. Search finds relevant Conversations without crossing Workspace boundaries.
- **FR-INBOX-02** Conversations support Open, Pending and Closed states. Agents can reply, add internal notes invisible to customers, apply tags, insert managed saved replies (All products or scoped to one or several Products; offered in the composer via `/` or a Saved button when the reply is All-products or its selection includes the conversation's Product; Workspace admins can also save the current draft as a new reply from the composer, without clearing or sending it) and see basic customer details and attachments.
- **FR-INBOX-03** A chat, later email handoff and subsequent replies can remain one Conversation. A Contact may be linked internally across Products, but unrelated Product history is not automatically shown in a Conversation.
- **FR-INBOX-04** Unread tracking is per agent and persistent: a customer Message is unread for an agent until that agent's durable read receipt exists (messages that predate the feature or arrive concurrently are never skipped). Read state is isolated per agent and Workspace. The signed-in page title counts unread customer Messages in OPEN and PENDING Conversations only — Closed Conversations never contribute (a customer reply reopens a Closed Conversation, so live unread never hides in one) — shown as (1)..(99), then (99+), with no prefix at zero. A customer Message is marked read only when displayed to that agent in a visible Conversation view (never from a background tab or prefetch), idempotently and in bounded batches; the count refreshes on focus/visibility, after successful mark-read writes, and via a bounded poll so other tabs and processes stay correct.
- **FR-INBOX-05** When a new Conversation (chat or email) has no agent reply within its Product's wait time (default 20 minutes, configurable per Product, can be switched off), the Workspace admins receive one email with the customer's messages and a link to the Conversation — at most once per Conversation, never after a reply, and without requiring any background service or external dependency. When no outbound mail provider is configured the setting says so and nothing is sent ([design/escalation.md](design/escalation.md)).
- **FR-INBOX-06** Every Conversation has a ticket number: a positive integer, unique within its Workspace, assigned once when the Conversation is created and never changed or reused (not even after the Conversation is deleted). Numbers start at 1 per Workspace and increase in creation order; concurrent creations through any channel (widget, inbound email, desk) never receive the same number. Existing Conversations are numbered in creation order when the feature is introduced. It is shown as a reference such as `SS-123` — in the widget thread (as "Reference SS-123"), in the inbox list and Conversation header, and as a `[SS-123]` tag in outbound email subjects (`Re: [SS-123] …`) — and agents can find a Conversation by typing it in search (`SS-123`, `#123` or `123`). The number is for humans only: inbound email still continues a Conversation by `Message-ID`/`In-Reply-To`/`References` or the reply token (FR-EMAIL-01), never by the subject or the number, and a chat-to-email continuation keeps the one number. Numbers are per Workspace, so another Workspace's number is never resolvable (FR-SEC-01).

## Widget and live chat

- **FR-CHAT-01** A Product's public embed key loads its widget with no secret in the page. In production the service enforces that the embedding origin is permitted for that Product. Development supports an explicit localhost path. An invalid key or origin cannot create or read Conversations.
- **FR-CHAT-02** A visitor can start live chat without an account or email. The service gives the visitor an unguessable, scoped session so they can resume their Conversation in the same browser; another visitor cannot read it by guessing IDs.
- **FR-CHAT-03** When support is available, visitor and agent messages appear in near real time. The UI reflects delivery/read only when the service can establish those states; disconnection and reconnection must not duplicate or lose messages.
- **FR-CHAT-04** When support is away, the widget presents a message form and requires a usable reply email before submission. The agent can answer the resulting Conversation by email. A visitor may also volunteer email during live chat for a later reply.
- **FR-CHAT-05** The widget works on desktop and mobile, supports keyboard use, isolates its styles, avoids host-page layout shift, survives SPA navigation and shows a recoverable error if the support service fails. It never downloads the dashboard application bundle; its size budget is tracked in [open-questions.md](open-questions.md).

## Developer context

- **FR-CTX-01** A small browser API lets an application explicitly identify the current user and attach structured application context to a visitor or Conversation, including useful account, plan, version, page and optional admin-link information. Context is optional and displayed beside the Conversation.
- **FR-CTX-02** Supplied identity and context are validated, bounded in size and depth, and rendered as untrusted data. The widget does not automatically inspect browser storage, form values, credentials or application secrets.

## Email and attachments

- **FR-EMAIL-01** Every Product can configure inbound support email, including a practical forwarding path. Valid inbound mail creates a Conversation for the addressed Product or continues the correct existing one using trustworthy threading/reply evidence (`Message-ID`, `In-Reply-To`, `References` or secure reply identifiers), never the subject alone. Attachments appear in the inbox.
- **FR-EMAIL-02** Agents reply from the inbox using a managed sender that makes the Product clear to the customer. If a chat visitor has supplied an email and leaves, a later response can continue the Conversation through email.
- **FR-EMAIL-03** Provider webhooks are signature-verified with replay protection. Repeated or forged delivery, malformed content, autoresponders, loops and oversized or unsafe attachments cannot create duplicate or unsafe support messages. Email HTML is safely presented. A failed delivery is visible for follow-up rather than silently treated as sent.
- **FR-FILE-01** Chat and email support file attachments subject to size limits, MIME validation (never the extension alone) and safe filenames, and are delivered non-executably. Only authorised Workspace users or the appropriate visitor can retrieve a file; deletion of its owning data also removes the file according to the documented cleanup process.

## Workspace API

- **FR-API-01** A Workspace Admin can create workspace-scoped API tokens in the dashboard (**Settings → API tokens**, hidden from Agents) and revoke them; scripts, CI and agents then call the Workspace API without a dashboard login or session cookie. A token has a name and an optional expiry (it stops working at the end of that day, UTC) and acts for its whole Workspace, never as a person. The full token (`ss_live_` prefix) is shown once at creation; only its SHA-256 hash is stored, and the list shows only the last four characters, creation, last-used and expiry times and revocation state. A revoked token stops working immediately; revoking again is harmless. Every token created in the dashboard carries three scopes today: `products:write` (reading and writing Products), `conversations:reply` (sending replies to customers) and `conversations:write` (internal notes, status and tags); tokens cannot be created or listed through the API, and a token minted before 2026-10-31 keeps only `products:write`. Planned, as amended 2026-10-29 ([ADR-0005](adr/0005-agent-first-workspace-api.md)): finer scopes limit what a token may do (FR-API-05; the dashboard scope picker and the interim default are open question AA7), and a token holding the `tokens:admin` scope can also list, create and revoke tokens through the API (FR-API-10), never with more scopes than its own; dashboard sessions remain the way to mint the first token. A token resolves to its own Workspace and can never read or change another Workspace's data, and another Workspace's Admin cannot revoke it (FR-SEC-01). Tokens work identically in hosted and self-hosted modes and need no Stripe, hosted API or external telemetry (FR-HOST-01). Detail: [api-tokens.md](api-tokens.md).
- **FR-API-02** A caller with a valid token can list and get Products (`GET /api/products`, `GET /api/products/{id}`), create a Product (`POST /api/products`) and edit one (`PATCH /api/products/{id}`), each returning the Product with its widget key and form key (`formKey`, `null` for a legacy Product that has none). Create and edit take the dashboard's validation and normalisation, including domains: create takes `domains` and `includeSiblings`; edit takes `name`, `primaryColor`, `addDomains`, `removeDomains` and `includeSiblings`, applied all together or not at all, and a request that changes nothing is refused. Archiving remains a dashboard action (FR-PROD-01). Writes accept tokens only and never a session cookie; reads accept a token or a signed-in Workspace Admin session. A request carrying an `Authorization` header is judged on the token alone. Another Workspace's Product id answers exactly like an unknown id. Every error has one JSON envelope, `{ "error": { "code", "message", "details"? } }`, with stable machine-readable codes (`invalid_request`, `unauthorized`, `forbidden`, `insufficient_scope`, `not_found`, `conflict`, `product_limit_reached`, `rate_limited`, `internal_error`); a presented token that is malformed, unknown, revoked or expired fails identically, so the caller cannot tell which. Abuse is bounded: at most 30 writes per minute per token, repeated failed token attempts from one client IP are throttled (20 per minute), request bodies are capped at 64 KiB, and each domain list holds at most 100 entries; a Workspace that already has 100 Products (archived included) cannot create another through the API (`409 product_limit_reached`; an abuse guard for a leaked token that the dashboard and onboarding do not share, so Products stay unlimited there); throttled requests answer `429` with `Retry-After`. Responses are `private, no-store`. Rate limits are in-process, so a multi-process self-hosted deployment enforces them per process.
- **FR-API-03** The Workspace API contract is published as an OpenAPI 3.1 document ([openapi.json](openapi.json)) that cannot silently drift from the implementation: an automated test compares its paths and methods, error codes and statuses, request and response schemas, limits and examples with the route files and validators, and the quickstart's calls with the spec. A public quickstart ([api-quickstart.md](api-quickstart.md)) takes a developer from a dashboard-created token to a Product with allowed domains and its widget key using plain HTTP, with the same steps on the hosted tier and self-hosted installations, differing only in the base URL (the installation's public URL, as documented in [self-hosting.md](self-hosting.md)).

### Agent-first Workspace API (planned)

Every requirement below is **planned** and not yet implemented. It follows [ADR-0005](adr/0005-agent-first-workspace-api.md) (decision) and [agent-api-plan.md](agent-api-plan.md) (phases, slices, tests, open questions). Phase 1 is FR-API-04..11 and FR-API-16..17 (the assignee clause of FR-API-08 and `conversations:assign` follow the assignment schema, AA4); phase 2 is FR-API-12..14; phase 3 is FR-API-15. Anything not decided is recorded in [open-questions.md](open-questions.md#agent-first-workspace-api-2026-10-29) and is not assumed here.

**Status, 2026-10-31.** Delivered so far: the scope registry, the Workspace-scoped data layer and `GET /api/v1/whoami` (FR-API-04 in part, FR-API-05..06 and FR-API-17 for the endpoints that exist), FR-API-07 and FR-API-11 for the write endpoints: signed cursors, the idempotency store (used by `POST /api/v1/conversations/{id}/messages` and `PATCH /api/v1/conversations/{id}`) and the append-only audit log (written for every token write and refused attempt by the `/api/v1` wrapper). Slice 1d (`createMessage`, `updateConversation`, FR-API-04 in part) lets a token send a reply or note and close, reopen or tag a Conversation. No endpoint uses cursors yet, and the audit log cannot be read through the API yet (`audit:read`, slice 1e).

- **FR-API-04** The Workspace API is versioned under `/api/v1`. `/api/products` and `/api/products/{id}` remain as a permanent alias with their current behaviour and response shape. List endpoints return `{ "items": [...], "nextCursor": string | null }` with `limit` (1-100) and an opaque `cursor`, and never a total count. `GET /api/v1/whoami` returns the token's own Workspace, token id and name, scopes and expiry. `POST /api/v1/conversations/{id}/messages` sends a reply (`conversations:reply`; it takes the dashboard's reply path, reopens a Closed Conversation, is `402 service_paused` while the Free-plan pause holds, and returns the delivery outcome) or adds an internal note (`conversations:write`); `PATCH /api/v1/conversations/{id}` changes status and tags together or not at all. A reply written through the API is shown in the inbox as `<token name> (API)`.
- **FR-API-05** A token carries granular scopes (planned set: `products:read|write`, `conversations:read|write|reply|assign|delete`, `contacts:read|delete`, `saved-replies:read|write`, `attachments:read`, `webhooks:read|write`, `tokens:admin`, `audit:read`, `workspace:read|write`, `team:write`, `billing:write`; `write` implies `read`). An operation without its scope answers `403 insufficient_scope`. Existing tokens keep working unchanged and gain nothing. Sending a reply to a customer requires `conversations:reply`, separate from notes, tags and status.
- **FR-API-06** The Workspace of an API request is determined only by the presented token. No path, query, body, header or cookie value selects or influences it. Every database access performed for `/api/v1` goes through one enforced Workspace-scoped data layer that cannot be bypassed from route code; models without a Workspace column are reached only through a Workspace-owned parent. A resource id from another Workspace (path, body, filter or cursor) is answered exactly like an unknown id: same status, body and headers, and the same amount of database work. No response, error, cursor, header, log line or webhook payload discloses another Workspace's data or the existence of its ids.
- **FR-API-07** Writes that create or send accept an `Idempotency-Key`: the same key and body replays the original response, a different body with the same key is `409 idempotency_conflict`, and keys are scoped to Workspace, token, method and resolved path (ids included) and expire after 24 hours. Sending a reply requires the key. Pagination cursors are opaque, signed and bound to the Workspace, route, parent ids and filters; any other cursor is `400 invalid_cursor`. Per-token read, write and reply rate limits and a per-IP limit apply, with `429` and `Retry-After`.
- **FR-API-08** With the matching scope a token can list Conversations (oldest first, as in the inbox; filters: status, Product, tag, Contact, search, updated-after), read one Conversation and its Messages, send a reply (the Conversation's chat or email route is used exactly as for a dashboard reply, with the delivery outcome in the response; a reply to a Closed Conversation reopens it; the Free-plan pause answers `402 service_paused`), add an internal note, change status, add and remove tags, list tags and (after assignment exists) set the assignee. A reply sent by a token is attributed to that token and shown in the inbox as such. Messages are append-only through the API.
- **FR-API-09** With the matching scope a token can list and read Contacts, delete a Contact or Conversation (FR-SEC-02), create, edit, list and delete saved replies, and read and upload attachments. Attachments are retrievable only with a token whose Workspace owns them, through an authenticated API path; there are no public or presigned attachment URLs.
- **FR-API-10** A token holding `tokens:admin` can list, create and revoke tokens of its own Workspace. A created token's scopes must be a subset of its creator's, an expiry is required (no server default, omission is `400`; the maximum is set in the plan; no expiry is dashboard-only), `tokens:admin` is never given to a token created through the API, the secret is returned once, and a token can revoke itself. Revocation is immediate and idempotent.
- **FR-API-11** Every token-authenticated write, token creation and revocation and every refused scope or cross-Workspace attempt is recorded in an append-only, Workspace-scoped audit log (token, operation, resource, request id, client IP, outcome, time; never bodies or secrets) that a token with `audit:read` can read. Refused attempts are bounded per token per hour so a flood of foreign ids cannot grow the log.
- **FR-API-12** A Workspace can subscribe HTTPS endpoints to its own events through the API (`webhooks:write`): conversation and contact created, status and tag changes, assignment, message received, message sent, message delivery failed, note created. Events are written in the same transaction as the change, delivered at least once with retries and backoff, listed in a delivery log, replayable, testable with a ping, and each subscription has a secret that can be rotated with an overlap. A subscription only ever receives events of its own Workspace.
- **FR-API-13** Webhook requests are signed (`SupportSeal-Signature` with timestamp and HMAC-SHA256 over the raw body, a documented replay window) and delivered under SSRF protection: HTTPS only, every resolved address must be public, the checked address is the one connected to, redirects are not followed, and timeouts and response sizes are bounded; the checks run at subscription time and again on every delivery attempt. A subscription that fails continuously is disabled and its admins are told.
- **FR-API-14** Creating a Product through the API returns, with the widget and form keys, everything needed to go live: the ready-to-paste widget snippet, the script URL, the Product's inbound email address and the form endpoint, with origins derived from the request, not from configuration.
- **FR-API-15** On the hosted tier an agent can create a Workspace through the API and receive a restricted bootstrap token, without a dashboard. Email verification and payment remain human steps: the token cannot send customer email, create tokens or invite members until the email is verified, and a billing endpoint returns plan and usage state and a Stripe Checkout URL for a human to open. The signup answer is identical for new and existing email addresses. Signup is rate-limited per IP and per address, unverified Workspaces are capped and expire. Self-hosted deployments have no API signup or billing routes and never need Stripe (FR-HOST-01).
- **FR-API-16** Every dashboard capability that changes or reads Workspace data has an API equivalent, or a recorded reason it does not. An automated test maps each dashboard server action to an API operation or a reasoned exemption and fails when a new action has neither.
- **FR-API-17** Each API endpoint ships with a two-Workspace (Alpha and Beta) integration test that calls it with the other Workspace's ids and asserts the unknown-id response and no data leakage, a coverage check that fails when an endpoint is untested, a lint and static test that fail when API route code reaches the database without Workspace scope, and fuzzing of guessed ids and cursors.

## Hosting, usage and safety

- **FR-HOST-01** The same core workflows run in hosted and self-hosted modes. A self-hosted installation represents exactly one Workspace (additional Workspaces are blocked, not merely unsupported) with multiple Products and agents, and operates without hosted billing, hosted APIs or external telemetry. Installation (environment, database, migrations, persistent volumes, storage, email, HTTPS/reverse proxy, security), backup and upgrade steps are documented, and the default installation is a straightforward `docker compose up` that adds no infrastructure (Redis, search engines, extra services) without a demonstrated need. External analytics and telemetry are off by default in self-hosted mode.
- **FR-USE-01** Hosted billing counts a Conversation once, when it is first opened, in the billing period in which it opened; message count does not matter. Replies, reopening and chat-to-email continuation of the same Conversation do not add another counted Conversation, and a Conversation is never counted again in a later billing period (decided 2026-09-25: counted once ever, per Conversation). Usage is auditable by Workspace and period.
- **FR-USE-02** Exceeding the hosted allowance does not abruptly reject new support messages: a grace period follows the moment the allowance is crossed. Workspace admins are notified by email as the allowance is approached and when it is exceeded, once per level per period; they see usage and plan options. On paid plans the grace period is at least 30 days and service never pauses; sustained overage is resolved by arranging a higher-volume plan (decided 2026-09-26, issue #15). On the Free plan the grace period is 7 days, admins get one reminder email per grace day with a link to Billing, and when it ends the Workspace's chat widget and contact form stop taking new messages (the widget shows a friendly "chat unavailable" notice) and agents cannot send replies, until the Workspace upgrades; the next month's allowance does not lift it (decided 2026-10-28). While paused, inbound email is still stored, the inbox stays readable, and notes, tags and status changes keep working; the dashboard shows every member why. The system never automatically upgrades a Workspace, never issues a surprise bill, never pauses service without a warning period, and never loses a stored customer message. Self-hosted installations have no allowance and are never paused (FR-HOST-01).
- **FR-USE-03** Hosted billing uses Stripe in USD and is separable from core support behaviour; paid plans do not limit Products and do not charge per agent. Hosted plans are Free, Pro (finite monthly Conversation allowance) and Business (unlimited Conversations), each paid plan billed monthly or annually. A Workspace picks the plan and interval at checkout. Current prices are recorded in docs/open-questions.md (M2). Self-hosted mode never requires it.
- **FR-SEC-01** Every read, write, search, widget action and attachment request enforces Workspace/Product ownership and the caller's role or visitor session. Cross-Workspace access fails even with a valid ID from another Workspace.
- **FR-SEC-02** The system supports deletion of Conversations, Contacts, Products, Workspaces, accounts and their attachments without orphaning personal data. Inputs, uploads, email and webhooks are treated as untrusted; secrets never appear in widget configuration, client bundles or routine logs. Rendering is XSS-safe and HTML is sanitised; sensitive endpoints enforce CSRF protection, rate limiting, secure headers, safe redirects and SSRF protection where relevant.
- **FR-OPS-01** Server logs are structured and carry request, Product and Conversation identifiers (Workspace where safe) so self-hosters can diagnose problems without a proprietary observability vendor; they never contain passwords, tokens, cookies, secrets or unnecessary message content.

## Acceptance path

In a clean browser: register → create Workspace → add Product A → embed and send live chat → answer from inbox and confirm the visitor receives it (with delivery/read state where available) → supply identity/context and an attachment → switch between all Products and Product A after adding Product B → apply note, tag and saved reply → test away email continuation → receive inbound Product B email, reply, and confirm outbound delivery. Run the same core flows in self-hosted mode. Separately attempt cross-Workspace access through URLs, APIs, widget keys, Conversation IDs and file URLs; all must fail. The cross-Workspace check uses two fully separate Workspaces (Alpha and Beta, Alpha with two Products, Beta with one; each with its own users, contacts, chat sessions, emails, attachments and developer context) and attempts access from one to the other through URLs, APIs, guessed IDs, attachment URLs, widget APIs, Conversation and Product IDs, and email endpoints. As Alpha's Admin, create an API token, create a Product and edit its domains with it, then confirm the same token cannot read or edit Beta's Product ids (FR-API-01..02) and a write without a token is refused. Once the agent-first API exists (FR-API-04..17), repeat this for every `/api/v1` endpoint: each is called with Beta's token and Alpha's real ids and must answer like an unknown id, Alpha's data must be unchanged, and webhook deliveries for Alpha events must never reach a Beta subscription.
